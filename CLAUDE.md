# CLAUDE.md — BidReady (RFP Compliance Matrix & Auto-Drafter)

This file governs every AI coding agent working in this repo. Read it fully before any change.
Companion docs: `PRODUCT_SPEC.md` (what to build), `ARCHITECTURE.md` (how it is built),
`TASKS.md` (what to do next), `DEV_SETUP.md` (how to run it), `DEMO.md` (hackathon demo script).

## 1. Working agreement

- Work from `TASKS.md`. Pick the first unchecked task in the current phase, do only that task,
  run its verification, then tick it (`[x]`) in the same change. Do not start the next task unasked.
- If a task is ambiguous or conflicts with `PRODUCT_SPEC.md` / `ARCHITECTURE.md`, stop and ask.
  Never silently expand scope; anything not in `PRODUCT_SPEC.md` "In scope" is out of scope.
- When you change a schema, endpoint, folder or convention, update `ARCHITECTURE.md` in the same change.
- Keep diffs small and focused. No drive-by refactors, renames or reformatting of untouched files.
- Never commit, push, or create branches unless the user asks.

## 3. Prohibitions

- **No new dependencies** (Python or npm) without asking first and stating why the existing stack cannot do it.
  Specifically banned: LangChain / LlamaIndex, axios (use `fetch` via the generated client), moment.js,
  lodash (use native JS), Redux / Zustand (TanStack Query + local state is enough), CSS-in-JS libraries,
  Bootstrap / MUI / Chakra, any ORM other than SQLModel, vector databases (ChromaDB etc.), LibreOffice.
- **No raw CSS files** beyond `frontend/src/index.css` (Tailwind entry + theme tokens). No inline `style={{}}`
  except for computed dimensions (e.g. a progress width). Use Tailwind utilities and shadcn components.
- **No hardcoded colours** in components; use theme tokens (`bg-background`, `text-muted-foreground`,
  status tokens defined in `index.css`).
- **No deprecated APIs:** Pydantic v1 syntax (`class Config`, `.dict()`, `validator`), FastAPI `@app.on_event`
  (use lifespan), `datetime.utcnow()` (use `datetime.now(UTC)`), React `defaultProps`, class components,
  `ReactDOM.render`, Tailwind v3 `tailwind.config.js` theme extension (v4 uses CSS `@theme`).
- **No secrets in code, logs, tests or fixtures.** Read them from settings only. Never print an API key.
- **Never log RFP or knowledge-base text** at INFO or above; log IDs and counts only.
- **No invented facts in AI output paths:** every drafted claim must go through citation + quote verification
  (see ARCHITECTURE §6). Do not weaken or bypass these guardrails, even in tests (use the offline provider instead).
- No `any` in TypeScript, no `# type: ignore` / `@ts-ignore` / `eslint-disable` without a one-line reason comment.
- No `print()` in backend code; use `logging.getLogger(__name__)`.
- No synchronous LLM or PDF work inside a request handler; long work goes through the job runner.

## 4. Coding guidelines

### Python (backend)
- Type hints on every function, including return types; `mypy --strict` must pass.
- Layering: `api/` (routers, HTTP only) → `services/` (business logic) → `pipeline/` (document/AI stages)
  → `models/` (SQLModel tables) and `schemas/` (Pydantic request/response). Routers never touch the DB
  session directly except through a service.
- One router per resource; route functions are thin: validate input, call service, return a schema.
- Errors: raise domain exceptions from `app/core/errors.py` (`NotFoundError`, `ValidationFailedError`,
  `LLMError`, `ConflictError`); a single exception handler maps them to JSON
  `{"error": {"code": "...", "message": "..."}}` with the right status. Never return bare 500s with stack traces.
- All LLM calls go through `get_llm(settings).complete(prompt_name, variables, schema, usage)` in
  `app/llm/client.py`, which validates output with the Pydantic schema and retries once. Every new prompt
  needs a `app/llm/prompts/<name>.md` file (`version:`, `---system---`, `---user---`) AND an offline handler
  in `app/llm/offline.py`. Never inline prompt text in code. Opus 5.5 rejects `temperature`; tune with `LLM_EFFORT`.
- Pure functions for scoring/formulas (go/no-go, page budgets, readiness) in `app/services/scoring.py`, unit-tested.
- Imports: stdlib, third-party, local — separated, sorted by ruff (`I` rules). Absolute imports from `app.`.
- Naming: `snake_case` functions/modules, `PascalCase` classes, `UPPER_SNAKE` constants.

### TypeScript (frontend)
- `strict: true`, `noUncheckedIndexedAccess: true`. Prefer `type` over `interface` except for props extension.
- Components: function components, one per file, `PascalCase.tsx`, named exports (no default exports
  except route modules if required). Props typed as `type XProps = {...}`.
- Folder by feature: `src/features/<feature>/{components,hooks,api.ts}`; shared UI in `src/components/ui`
  (shadcn, do not hand-edit except theme tweaks) and `src/components/common`.
- Server state only via TanStack Query hooks in `features/*/api.ts`; query keys from `src/lib/queryKeys.ts`.
- API calls only through `src/lib/api.ts` (typed `fetch` wrapper using generated `src/types/api.ts`).
  Regenerate types with `pnpm gen:api` after any backend schema change.
- Every async UI state handles loading, empty, and error explicitly (see ARCHITECTURE §8).
- Imports: use the `@/` alias; order: react, third-party, `@/` internal, relative; no deep relative `../../..`.
- Accessibility: every icon-only button has `aria-label`; status is never conveyed by colour alone.

### Tests
- Backend: pytest with the offline LLM provider and hash embeddings (see `tests/conftest.py`); jobs run inline;
  the generated files in `samples/` are the fixtures. Tests never call a network API.
- Frontend: Vitest + Testing Library for components with logic; no snapshot tests.
- A task is done only when `make check` passes (lint + types + tests for both apps).

## 5. Terminal rules

- Always non-interactive: `pnpm install --frozen-lockfile` (or `pnpm install` when adding an approved dep),
  `uv sync`, `CI=1 pnpm dlx shadcn@latest add <component> --yes </dev/null`, `pnpm test` (runs once; `pnpm test:watch` for watch mode), `alembic upgrade head`, `git --no-pager`.
- Never run: `rm -rf` outside `backend/data/` or build output dirs, `git push`, `git reset --hard`,
  `git clean`, global installs (`npm i -g`, `pip install` outside uv), `sudo`, or anything touching `~/.ssh`.
- Do not start long-running servers in the foreground of a tool call; run dev servers in the background
  and stop them when done.
- Prefer `make` targets (see `DEV_SETUP.md`) over ad-hoc commands so results are reproducible.
- Database: never edit `app.db` by hand; schema changes only via a new Alembic revision
  (`make migration m="message"`), reviewed before `make migrate`.
